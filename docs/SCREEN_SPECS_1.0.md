# 인사야 1.0 화면 명세

> 상태: 제품/UX 개발 기준
> 기준일: 2026-08-14
> 상위 문서: `PRODUCT_PLAN_1.0.md`, `UX_FLOW_1.0.md`, `CASE_MODEL_1.0.md`

## 1. 목적

이 문서는 인사야 1.0에서 실제로 구현할 화면과 각 화면의 책임을 정의한다.

핵심 원칙은 다음과 같다.

1. 사용자가 첫 화면에서 선택해야 할 것은 하나여야 한다.
2. 사건이 생성된 뒤에는 모든 기능이 Case를 중심으로 동작한다.
3. 독립 도구는 유지하되 제품의 주 흐름을 방해하지 않는다.
4. 한 화면에는 하나의 Primary Action만 둔다.
5. 사용자가 항상 현재 단계와 다음 행동을 알 수 있어야 한다.

## 3. Screen 01 — Home

### 목적

사용자가 고민 없이 자신의 노동문제를 입력하게 한다.

### 핵심 질문

> 회사에서 무슨 일이 있었나요?

### 화면 구성

```text
[Header]
인사야                        가이드  전문가 찾기  내 사건

[Hero]
노동문제, 어디서부터 해야 할지 모르겠다면
상황부터 정리해 드릴게요.

[문제 입력창                                  →]
예: 퇴사했는데 마지막 월급이 아직 안 들어왔어요.

[대표 상황]
임금이 밀렸어요 / 해고 통보를 받았어요 / 퇴직금을 못 받았어요

[신뢰 정보]
적용 기준일 표시 · 개인정보 최소수집 · 공식 근거 연결

[보조 영역]
계산기 찾기 · 문서 찾기 · 노동 가이드
```

### Primary Action

`문제 해결 시작하기`

입력 자체가 Primary Action이므로 별도의 큰 CTA를 중복하지 않는다.

### 제거/축소

- 홈 상단의 계산기/문서/노무사/상황별 해결 4개 대형 카드 제거
- 업데이트 소식 CTA는 하단 또는 푸터로 이동
- 기능 개수 강조 문구는 Product Proof 영역으로 이동

### 생성되는 데이터

- rawInput
- tentativeCaseType
- startedAt

### 성공 조건

사용자가 페이지 진입 후 다른 메뉴를 학습하지 않고 문제를 입력할 수 있다.

## 4. Screen 02 — Case Intake

### 목적

AI가 자유 대화를 길게 이어가는 대신 사건 판단에 필요한 사실을 짧고 구조적으로 확인한다.

### 레이아웃

Desktop:

```text
[Case Header]
임금체불 사건                  2/5 확인 중

┌ 대화/질문 영역 ─────────────┬ 현재 확인된 내용 ┐
│                             │                  │
│ AI 질문                     │ ✓ 퇴사 상태      │
│ [선택지/입력]               │ ✓ 7월 급여 미지급 │
│                             │ ? 지급일          │
│                             │ ? 급여명세서      │
└─────────────────────────────┴──────────────────┘
```

Mobile:

```text
사건 제목 / 진행도
질문
입력
현재 확인된 내용 접기/펼치기
```

### 질문 규칙

- 한 번에 1~3개 질문
- 선택형으로 답할 수 있으면 선택형 우선
- 날짜/금액은 전용 입력 사용
- 이미 확보한 사실은 다시 묻지 않음
- 사용자가 모르는 항목은 `모름` 상태로 저장

### 상태 표시

- 확인됨
- 추가 확인 필요
- 사용자 모름
- 계산 필요

### Primary Action

`다음 확인`

### Secondary Action

`지금까지 내용으로 먼저 보기`

완전한 정보를 강제하지 않는다.

## 5. Screen 03 — Case Analysis

### 목적

수집된 사실을 Case Report 초기 버전으로 변환한다.

### 화면 구성

```text
분석이 완료됐어요

[사건 요약]
현재 확인된 내용으로는 임금 미지급 쟁점이 있습니다.

[확인 상태]
확인된 사실 6개
추가 확인 2개

[예상 금액]
현재 계산 가능 / 추가 입력 필요

[중요 정보]
적용 기준일
주요 근거

[다음 행동]
체불액 정확히 계산하기
```

### 반드시 구분할 정보

- 확인된 사실
- 추정
- 추가 확인 필요

### Primary Action

Case별 `Next Best Action` 하나

예:

- 체불액 계산하기
- 해고 통지서 확인하기
- 퇴직 전 3개월 임금 입력하기

### 금지

계산기/문서/노무사/공식절차 버튼을 같은 위계로 4개 나열하지 않는다.

## 6. Screen 04 — Case Workspace

### 목적

인사야 1.0의 핵심 화면. 하나의 사건을 해결하기 위한 현재 상태와 다음 행동을 지속 관리한다.

### Desktop 기본 구조

```text
┌─────────────────────────────────────────────────────┐
│ 임금체불 · 진행 중                      적용기준 2026-08 │
│ 마지막 업데이트 3분 전                              │
└─────────────────────────────────────────────────────┘

┌ 사건 진행 ──────────────┐  ┌ 다음 행동 ───────────────┐
│ ✓ 상황 확인             │  │ 체불액을 정확히 계산하세요 │
│ ✓ 쟁점 확인             │  │ [계산 계속하기]            │
│ ● 금액 계산             │  └───────────────────────────┘
│ ○ 증거 정리             │
│ ○ 해결 준비             │
└────────────────────────┘

[핵심 카드]
예상 금액 | 중요 날짜 | 확보 증거 | 상담 필요도

[탭]
개요 | 사실 | 금액 | 증거 | 행동 | 문서 | 근거
```

### Mobile 기본 구조

```text
사건 제목
진행도

[다음 행동 카드]

예상 금액 / 중요 날짜

[섹션 아코디언]
사실
금액
증거
행동
문서
근거
```

### Case Header

표시:

- Case title
- caseType
- status
- progress
- appliedRuleDate/asOfDate
- updatedAt

### Progress

Progress는 단순 퍼센트가 아니라 단계 기반이다.

```text
1 상황 정리
2 판단 준비
3 금액/조건 확인
4 증거 정리
5 해결 준비
```

사건 유형별 세부 단계는 다를 수 있지만 최상위 구조는 통일한다.

## 7. Workspace — Overview

### 목적

사용자가 사건 전체를 10초 안에 이해한다.

표시:

- 한 문장 사건 요약
- 현재 판단
- 가장 중요한 미확인 사실
- 예상 금액
- 가장 가까운 중요 날짜
- 증거 확보 현황
- Next Best Action

### Primary Action

현재 상태에서 가장 중요한 행동 하나.

---

## 8. Workspace — Facts

### 목적

AI 대화에서 추출한 사실을 사용자가 확인·수정할 수 있게 한다.

### 구조

```text
확인된 사실
✓ 퇴사일 2026-08-01
✓ 월급 3,000,000원
✓ 매월 10일 지급

확인 필요
? 7월 급여명세서 보유 여부
? 연장근로 포함 여부
```

### 기능

- 수정
- 삭제
- 직접 추가
- 출처 표시: 사용자 입력 / 계산 / 문서

AI가 추출한 사실을 사용자가 최종적으로 통제한다.

---

## 9. Workspace — Money

### 목적

사건과 관련된 계산 결과를 한 곳에 모은다.

### 예: 임금체불

```text
미지급 기본급        3,000,000원
연장근로수당          계산 필요
미사용 연차수당       해당 여부 확인
──────────────────
현재 확인된 체불액    3,000,000원+
```

### 규칙

- 숫자가 확정되지 않으면 범위 또는 `계산 필요` 표시
- 계산 근거 표시
- 입력값 수정 가능
- 계산기 이름보다 사건의 의미를 먼저 표현

잘못된 예:

`연장·야간·휴일 계산기`

좋은 예:

`추가로 받지 못한 연장근로수당 확인`

## 10. Workspace — Evidence

### 목적

법률 설명보다 실제 해결에 필요한 자료를 준비시킨다.

### 구조

```text
필수에 가까움
□ 근로계약서
□ 급여명세서
□ 계좌 입금내역

있으면 도움됨
□ 출퇴근 기록
□ 회사와 주고받은 메시지
```

### 상태

- 있음
- 없음
- 확보 예정
- 해당 없음

### 파일 업로드

1.0 초기에는 파일 내용 자동분석보다 `보유 여부` 관리가 우선이다.
파일 업로드/문서 분석은 별도 보안 설계 후 확장한다.

---

## 11. Workspace — Actions

### 목적

사용자가 해결 순서를 안다.

### 구조

```text
1. 회사에 지급일 확인 요청        완료
2. 미지급 금액 정리              진행 중
3. 요청 문서 작성                대기
4. 공식 절차 검토                대기
5. 필요 시 전문가 상담           선택
```

각 행동은 다음을 갖는다.

- 상태
- 이유
- 필요한 선행 조건
- 연결 도구
- 외부 공식기관 링크(필요 시)

### 원칙

전문가 상담을 무조건 마지막 단계로 강제하지 않는다.
긴급·고위험 사건은 조기 상담을 권할 수 있다.

---

## 12. Workspace — Documents

### 목적

24종 문서센터를 Case에 연결한다.

### 표시 방식

`문서 목록`이 아니라 `지금 필요한 문서`를 먼저 보여준다.

```text
추천
내용증명 초안
현재 사건 정보 8개 자동 입력 가능
[초안 만들기]

추가 문서
노동청 진정서
```

### 원칙

- Case fact 자동 프리필
- 사용자가 최종 검토
- 문서 버전/출처 표시
- 독립 문서센터는 계속 유지

---

## 13. Workspace — Sources

### 목적

AI 신뢰감을 문장 표현이 아니라 근거 구조로 제공한다.

### 표시

```text
적용 기준일
2026-08-01

주요 근거
근로기준법 ○조
적용기간: 2026-...
마지막 검증: 2026-08-...

공식 출처 보기 ↗
```

### 원칙

시행 예정 법령은 `현재 적용`과 시각적으로 분리한다.

## 14. Screen 05 — My Cases

### 1.0 범위

로그인 계정 시스템을 즉시 만들지 않더라도 UI 개념은 설계한다.

```text
내 사건

진행 중
임금체불                  다음: 금액 확인
2026-08-14

완료
퇴직금                    해결 준비 완료
```

### 초기 구현 옵션

Case 저장 방식은 기술/개인정보 설계 단계에서 결정한다.
화면은 저장 방식과 분리해서 설계한다.

## 15. 독립 Calculator Library

유지한다.

역할:

- 검색 유입
- 이미 목적이 명확한 사용자
- Case 없이 빠른 계산

변경:

계산 완료 후 CTA를 `AI 상담`로 단순 이동시키지 않고:

`이 계산 결과로 사건 정리하기`

를 제공한다.

---

## 16. 독립 Document Library

유지한다.

변경:

- 24종 개수보다 상황별 그룹 강조
- 작성 완료 후 Case 생성/연결 선택 제공
- 공식/표준 양식 여부와 기준 버전 표시

---

## 17. Expert Directory

유지하되 글로벌 핵심 CTA에서 한 단계 낮춘다.

Case 안에서는:

```text
전문가 상담 필요도 높음
이 사건 요약을 가지고 상담할 수 있습니다.
[노무사 정보 보기]
```

독립 검색도 계속 제공한다.

---

## 18. Employer Entry

근로자 중심 1.0 출시를 방해하지 않도록 별도 진입으로 분리한다.

```text
사업주이신가요?
노무 리스크 사전 점검 →
```

기존 사업주 가이드·계산·문서는 보존한다.

---

## 19. 공통 상태 화면

모든 주요 화면은 다음 상태를 설계한다.

### Loading

- Skeleton
- 현재 수행 중인 작업 설명

### Empty

- 왜 비어 있는지
- 다음 행동

### Error

- 무엇이 실패했는지
- 사용자 입력이 보존됐는지
- 재시도

### Partial

AI나 외부 연결 일부가 실패해도 이미 확보한 Case 데이터는 보여준다.

## 22. 화면 승인 기준

각 화면은 구현 전에 다음을 만족해야 한다.

- 화면 목적을 한 문장으로 설명할 수 있음
- Primary Action이 하나임
- Case의 어떤 데이터를 읽고 쓰는지 정의됨
- 모바일 구조가 정의됨
- Loading/Empty/Error 상태가 있음
- 법률 판단과 AI 설명의 역할이 구분됨
- 기존 기능을 중복 구현하지 않음
