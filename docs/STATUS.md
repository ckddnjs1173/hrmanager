## 2. 프론트엔드 상태

현재 프론트는 기능량은 충분하지만 `index.html` 중심의 대형 SPA에 많은 UI·콘텐츠·계산 로직이 결합되어 있다.

제품화 문제:

- 기능별 진입점이 많아 사용자가 다음 행동을 직접 선택해야 한다.
- AI 상담, 상황별 해결, 계산기, 문서, 노무사 찾기가 각각 강한 기능으로 경쟁한다.
- 디자인 패턴이 기능 추가 과정에서 누적됐다.
- 핵심 사용자 여정이 하나의 `Case` 진행 상태로 표현되지 않는다.

따라서 전면 재작성보다 기능을 보존하며 점진적으로 분리한다.

## 8. 기존 기획문서 상태

현재 루트에는 다음 문서들이 함께 존재한다.

- `BENCHMARK.md`
- `CLAUDE.md`
- `CONTENT.md`
- `DESIGN.md`
- `HARVEST.md`
- `LAUNCH.md`
- `MASTERPLAN.md`
- `OPERATIONS.md`
- `PAGES.md`
- `POLISH.md`
- `PRODUCT.md`
- `UPGRADE.md`
- `기획-어시스턴트전환.md`

이 문서들은 유효한 아이디어가 많지만 작성 시점과 실제 구현 상태가 다르다.

새 기준:

- 제품 방향: `docs/PRODUCT_PLAN_1.0.md`
- 실제 구현 상태: `docs/STATUS.md`
- 레포 개편: `docs/REPO_REFACTOR_PLAN.md`

기존 문서는 즉시 삭제하지 않고 필요한 내용을 흡수한 뒤 archive로 이동한다.

## 10. 결론

인사야의 현재 문제는 기능 부족이 아니다.

가장 큰 제품 과제는 **이미 만든 기능을 하나의 사건 해결 경험으로 통합하고, 이를 안정적으로 반복 개발할 수 있는 코드·테스트·문서 구조를 만드는 것**이다.
