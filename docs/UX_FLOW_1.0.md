# 인사야 1.0 핵심 UX 흐름

> 상태: 개발 기준 문서
> 기준일: 2026-08-14
> 상위 문서: `PRODUCT_PLAN_1.0.md`

## 1. 목표

인사야 1.0의 UX 목표는 기능을 많이 보여주는 것이 아니라, 사용자가 노동문제를 설명한 뒤 **다음 행동을 잃지 않고 사건 해결 준비를 끝내게 하는 것**이다.

핵심 흐름은 하나다.

```text
홈
→ 문제 입력
→ 사건 생성
→ 필수 사실 확인
→ 사건 분석
→ 내 사건 Workspace
→ 계산·증거·문서·공식절차
→ 완료 또는 전문가 상담
```

계산기·문서센터·가이드·노무사 찾기는 독립 제품이 아니라 이 흐름을 지원하는 엔진/보조 진입점이다.

---

## 2. 글로벌 정보구조

### 데스크톱 헤더

```text
[인사야]   문제 해결하기   가이드   전문가 찾기                 내 사건
```

원칙:

- Primary CTA는 `문제 해결하기`.
- `계산기`, `문서센터`는 최상위 핵심 메뉴에서 내린다.
- 기존 독립 도구 URL/SEO 진입은 유지한다.
- 사업주 영역은 근로자 사건 해결 UX와 혼합하지 않는다.

### 모바일 하단 내비게이션

```text
홈 | 해결하기 | 가이드 | 내 사건
```

전문가 찾기는 사건 내부와 메뉴에서 접근 가능하게 한다.

---

## 3. Screen A — 홈

### 목적

사용자가 5초 안에 “여기에 내 상황을 적으면 된다”는 것을 이해하게 한다.

### Above the fold

```text
인사야

회사에서 무슨 일이 있었나요?
노동문제를 설명하면 확인할 사실부터 다음 행동까지 정리해드립니다.

┌─────────────────────────────────┐
│ 예: 퇴사했는데 마지막 월급을 못 받았어요 │
└─────────────────────────────────┘
                    [문제 해결 시작하기]

[월급이 밀렸어요] [해고 통보를 받았어요]
[퇴직금을 못 받았어요] [야근수당이 궁금해요]
```

### 그 아래

1. 인사야가 해주는 일 4단계
   - 상황 정리
   - 금액/쟁점 확인
   - 증거/문서 준비
   - 해결 경로 안내
2. 많이 해결하는 문제
3. 신뢰 블록
   - 공식 근거 기반
   - 개인정보 최소 수집
   - AI 정보 제공 범위 고지
4. 가이드/계산기는 하단 보조 콘텐츠

### 제거/축소

- 첫 화면에서 27개 계산기 목록 노출 금지
- 첫 화면에서 24개 문서 목록 노출 금지
- 여러 Primary CTA 병렬 배치 금지
- 장문의 서비스 소개 금지

## 4. Screen B — 사건 생성 / Intake

### 진입

홈에서 사용자가 자유문장을 입력하면 즉시 하나의 Case를 만든다.

예:

```text
“회사에서 3개월째 월급을 안 줍니다.”
```

### 화면 구조

데스크톱:

```text
┌───────────────────────────────┬──────────────────────┐
│ 대화 / 질문                    │ 사건 요약             │
│                               │                      │
│ 인사야: 임금체불 문제로 보여요. │ 임금체불              │
│ 먼저 2가지만 확인할게요.        │ 확인된 사실 2/6        │
│                               │ 진행도 20%            │
│ [현재 재직 중인가요?]           │                      │
│ ○ 재직 중  ○ 퇴사              │                      │
│                               │                      │
└───────────────────────────────┴──────────────────────┘
```

모바일:

- 대화/질문이 본문
- 사건 요약은 상단 축약 카드 또는 bottom sheet

### 질문 원칙

- 한 번에 1~3개
- 사용자가 이미 말한 내용은 다시 묻지 않는다.
- 선택형으로 답할 수 있으면 선택형을 우선한다.
- 금액/날짜는 전용 입력 UI를 사용한다.
- 사용자가 모르면 `모르겠어요` 선택을 제공한다.
- 필수 사실과 선택 사실을 구분한다.

### Intake 상태

```text
case_created
→ collecting_facts
→ ready_for_analysis
```

## 5. Screen C — 사건 분석 결과

충분한 핵심 사실이 모이면 대화 답변을 길게 출력하는 대신 `Case Report`를 생성한다.

### Case Report 구조

```text
[임금체불 가능성 검토]

현재 확인된 내용
✓ 퇴사 상태
✓ 월 급여 300만원
✓ 2개월분 미지급

추가 확인 필요
! 급여 지급일
! 마지막 정상 지급일

현재 판단
임금 미지급 쟁점이 있습니다.
확정 판단을 위해 위 2개 항목을 추가 확인해야 합니다.

예상 금액
약 6,000,000원
[계산 상세 보기]

준비할 증거
2 / 5 준비됨
[증거 확인하기]

다음 행동
1. 미지급 금액 확정
2. 회사에 지급 요청
3. 미지급 지속 시 공식 절차 준비

[다음 단계 진행하기]
```

### 핵심 원칙

- 확인된 사실 / 추정 / 미확인을 시각적으로 구분한다.
- 금액은 계산 엔진의 결과를 사용한다.
- 법률 근거는 `근거 보기`로 접어둘 수 있다.
- 화면 최하단 Primary CTA는 하나다.

## 6. Screen D — 내 사건 Workspace

`내 사건`은 인사야 1.0의 핵심 화면이다.

### 상단

```text
임금체불 사건
진행 중 · 마지막 업데이트 8월 14일

진행도 60%
[████████████░░░░░░]
```

### 핵심 카드 순서

#### 1. 다음 행동

항상 최상단.

```text
다음으로 할 일
급여명세서를 확인해 미지급 금액을 확정하세요.

[금액 확인하기]
```

#### 2. 현재 판단

- 현재 사건 유형
- 핵심 쟁점
- 판단 수준
- 추가 확인 필요 여부

#### 3. 예상 금액

- 계산 결과
- 계산 기준
- 입력값
- 다시 계산

#### 4. 증거

```text
✓ 근로계약서
✓ 계좌 입금내역
○ 급여명세서
○ 출퇴근 기록
```

#### 5. 중요 기한

- 특정 기한이 있는 경우 우선 노출
- 기한이 불확실하면 억지로 날짜를 만들지 않는다.

#### 6. 행동 계획

```text
✓ 상황 정리
✓ 체불액 계산
○ 지급 요청
○ 공식 절차 준비
○ 필요 시 전문가 상담
```

#### 7. 문서

사건에 필요한 문서만 노출한다.

```text
내용증명 초안
노동청 진정 준비자료
```

#### 8. 근거

- 적용 법령
- 공식 출처
- 기준일
- 검증 상태

#### 9. 전문가 상담

후단 선택지.

```text
이 사건은 전문가 검토가 도움이 될 수 있습니다.
[상담용 사건 요약 만들기]
[노무사 찾기]
```

## 7. 기존 기능을 Workspace에 연결하는 방식

### 상황별 해결

기존 `SOLVE` 시나리오는 폐기하지 않는다.

변경:

```text
상황별 해결 카드
→ 단순 가이드 페이지
```

에서

```text
대표 사건 템플릿
→ Case 생성
→ 필요한 사실 프리셋
→ Workspace
```

으로 바꾼다.

### 계산기

독립 계산기는 SEO/직접 사용을 위해 유지한다.

Case에서 호출될 때:

```text
Case facts
→ calculator input prefill
→ deterministic calculation
→ result 저장
→ Case Report 반영
```

### 문서센터

독립 문서센터는 유지하되 Case 내부에서는 전체 목록을 보여주지 않는다.

```text
사건 유형 + 진행 단계
→ 지금 필요한 문서만 추천
→ Case facts 자동채움
→ 생성 결과 Case에 저장
```

### 상담요약서

기존 별도 산출물에서 `Case Report의 전문가 전달 버전`으로 흡수한다.

### 노무사 찾기

항상 노출하는 판매 CTA가 아니라 해결 과정 후단의 선택지로 둔다.

## 8. 핵심 사건 5종의 UX 우선순위

### 1. 임금체불

```text
미지급 여부
→ 기간/임금 확인
→ 예상 체불액
→ 증거
→ 지급요청
→ 공식절차
```

### 2. 해고·권고사직

```text
종료 방식
→ 통보 방식/일자
→ 사업장/근속 등 사실 확인
→ 핵심 쟁점
→ 증거
→ 기한/구제절차
```

### 3. 퇴직금

```text
퇴직 여부
→ 근속기간
→ 임금정보
→ 대상 여부
→ 예상액
→ 미지급 대응
```

### 4. 근로시간·수당

```text
근무시간
→ 근로형태
→ 임금구조
→ 시간/수당 계산
→ 기록 증거
→ 미지급 대응
```

### 5. 연차

```text
입사일/근속
→ 출근/사용 정보
→ 발생/잔여
→ 수당 또는 사용 문제
→ 행동
```

## 9. 화면 상태 기준

모든 핵심 화면은 다음 상태를 설계해야 한다.

- loading
- empty
- partial
- success
- validation_error
- server_error
- AI_unavailable
- stale_case

AI가 실패해도 Case 자체가 사라지면 안 된다.

가능한 결정론적 기능(계산기, 체크리스트, 저장된 사실, 문서)은 계속 사용할 수 있어야 한다.

---

## 10. 모바일 원칙

- 핵심 행동 버튼은 thumb reach 영역에 둔다.
- 사건 진행도는 항상 빠르게 확인 가능해야 한다.
- 긴 Case Report를 한 카드에 몰지 않는다.
- 판단/금액/증거/행동을 섹션 카드로 분리한다.
- 대화 중 Case 요약은 bottom sheet로 확인한다.
- 문서 작성은 단계형 폼을 우선한다.

---

## 11. 제품 성공 기준

첫 번째 제품 릴리스에서 측정할 핵심 이벤트:

```text
case_started
case_core_facts_completed
case_report_generated
calculation_completed
case_evidence_checked
case_document_created
official_action_opened
expert_handoff_started
case_completed
```

핵심 퍼널:

```text
문제 입력
→ 핵심 사실 완료
→ Case Report 생성
→ 다음 행동 실행
```

단순 페이지뷰나 채팅 메시지 수보다 이 퍼널을 우선한다.

## 12. 구현 순서

1. Case 데이터 모델
2. Case 생성 API
3. 기존 상담 결과를 Case Report 구조로 변환
4. 홈 입력 → Case 생성 연결
5. Workspace 기본 UI
6. 임금체불 Case 완성
7. 해고
8. 퇴직금
9. 근로시간·수당
10. 연차
11. 기존 계산기/문서/노무사 진입을 Case에 연결

새 기능 추가보다 이 흐름 완성이 우선이다.
