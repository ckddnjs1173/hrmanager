# 인사야 Product Plan 1.0

> **상태:** 제품 기준 문서 (Source of Truth)
> **기준일:** 2026-08-14
> **대상:** 인사야 1.0 제품화
> **원칙:** 신규 기능 수를 늘리는 것보다 기존 기능을 하나의 해결 경험으로 통합한다.

---

## 1. 제품 정의

### 한 문장 정의

**인사야는 근로자가 노동문제를 설명하면, 사건을 구조화하고 판단에 필요한 사실·예상 금액·증거·기한·문서·공식 해결 경로까지 한 곳에서 준비하게 하는 AI 노동문제 해결 서비스다.**

### 인사야가 아닌 것

- 노동법 백과사전이 아니다.
- 계산기 27종을 모아둔 도구 사이트가 아니다.
- 문서 양식 24종을 모아둔 서식 사이트가 아니다.
- ChatGPT를 노동법 프롬프트로 감싼 채팅 서비스가 아니다.
- 특정 노무사를 추천·배정하는 중개 서비스가 아니다.

### 인사야가 해결해야 하는 핵심 질문

사용자가 노동문제를 겪었을 때 보통 다음을 모른다.

1. 이게 법적으로 문제가 되는 상황인가?
2. 내 상황에서 추가로 확인해야 할 사실은 무엇인가?
3. 받을 수 있는 돈 또는 부담할 위험은 얼마인가?
4. 어떤 증거를 확보해야 하는가?
5. 놓치면 안 되는 기한이 있는가?
6. 지금 무엇부터 해야 하는가?
7. 어떤 문서가 필요한가?
8. 어디에 신고·신청해야 하는가?
9. 전문가 상담이 필요한 수준인가?

인사야 1.0은 이 9개 질문에 하나의 사건 흐름으로 답해야 한다.

---

## 2. 핵심 사용자

### Primary: 근로자

초기 제품의 가장 중요한 사용자는 노동문제가 이미 발생했거나 발생할 가능성이 높은 근로자다.

핵심 사건군:

- 임금체불
- 퇴직금
- 해고·권고사직
- 연장·야간·휴일근로 및 수당
- 주휴수당
- 연차
- 근로계약
- 직장 내 괴롭힘·성희롱
- 산재
- 실업급여

### Secondary: 사업주

사업주 기능은 유지하되 근로자 문제 해결 흐름과 UI를 혼합하지 않는다.

사업주 제품의 핵심 가치는 **분쟁 발생 후 대응**보다 **노무 리스크 예방·계약·임금·근태·해고 전 점검**이다.

### Tertiary: 공인노무사

노무사는 사용자 문제 해결의 후단에 위치한다.

- 프로필·분야·지역 정보 제공
- 이용자가 비교·선택
- 이용자 동의 후 사건 요약 전달
- 향후 입점·노출·예약관리 SaaS 과금
- 사건 성사·수임료와 연동된 수수료 모델은 사용하지 않는다.

## 3. North Star Experience — `내 사건`

인사야의 핵심 제품 객체는 채팅이 아니라 **사건(Case)** 이다.

사용자는 한 번의 대화를 소비하는 것이 아니라 하나의 노동문제를 해결해 나간다.

### 사건의 기본 구조

```text
내 사건
├─ 사건 유형
├─ 상황 요약
├─ 핵심 사실
├─ 미확인 사실
├─ 쟁점
├─ 잠정 판단
├─ 예상 금액 / 계산 결과
├─ 중요 기한
├─ 증거 체크리스트
├─ 행동 계획
├─ 생성 문서
├─ 공식기관 경로
├─ 전문가 상담 필요도
└─ 진행 상태
```

### 사건 진행도 예시

```text
김○○님의 임금체불
진행도 60%

✓ 상황 정리
✓ 체불 가능성 확인
✓ 예상 체불액 계산
○ 증거 2개 추가 확인
○ 회사에 지급 요청
○ 노동청 진정 준비
○ 필요 시 노무사 상담
```

### 핵심 원칙

- 채팅은 사건 정보를 수집하는 입력 UI다.
- 계산기는 사건의 숫자를 검증하는 엔진이다.
- 문서센터는 사건 데이터를 이용해 문서를 만드는 엔진이다.
- 가이드는 사건 이해를 돕는 보조 콘텐츠다.
- 노무사 찾기는 사건 해결의 선택적 후속 단계다.

각 기능이 독립적으로 경쟁하지 않고 `Case`를 중심으로 연결되어야 한다.

## 4. 핵심 사용자 여정

### 4.1 최초 진입

```text
홈
↓
"회사에서 무슨 일이 있었나요?"
↓
한 문장 입력 또는 대표 상황 선택
↓
사건 생성
```

첫 화면의 Primary CTA는 하나만 둔다.

**문제 해결 시작하기**

계산기·문서·노무사·가이드는 첫 화면에서 보조 진입점으로만 제공한다.

### 4.2 사건 Intake

AI가 자유 대화를 길게 이어가는 대신 사건 유형에 필요한 필수 사실을 구조적으로 확인한다.

예: 임금체불

- 재직/퇴직 여부
- 미지급 임금 종류
- 미지급 기간
- 약정 임금
- 지급일
- 근로계약서 여부
- 급여명세서 여부
- 사업장 및 근로형태

질문은 한 번에 과도하게 묻지 않고 1~3개씩 진행한다.

### 4.3 사건 분석

분석 결과는 채팅 문장만으로 끝나지 않는다.

고정된 `Case Report`에 반영한다.

```text
사건 요약
현재 확인된 사실
추가 확인 필요
핵심 쟁점
현재 판단
예상 금액
증거
기한
행동 순서
근거
```

### 4.4 해결 실행

Case Report 하단에는 상황에 맞는 **다음 행동 하나**를 가장 강하게 노출한다.

예:

- `체불액 정확히 계산하기`
- `해고 통보 증거 정리하기`
- `내용증명 초안 만들기`
- `노동청 진정 준비하기`

모든 기능으로 동시에 보내지 않는다.

### 4.5 사건 완료

사건의 마지막은 세 가지 중 하나다.

1. 스스로 해결 준비 완료
2. 공식기관 절차로 이동
3. 공인노무사 상담 준비 완료

인사야의 성공은 사용자가 오래 머무는 것이 아니라 **다음 해결 행동을 명확하게 실행하는 것**이다.

## 5. 정보구조(IA) 1.0

### 글로벌 내비게이션

```text
인사야 | 문제 해결하기 | 가이드 | 전문가 찾기 | 내 사건
```

도구는 별도 최상위 메뉴로 강조하지 않는다.

### 제품 구조

```text
인사야
├─ 문제 해결하기
│  ├─ 사건 생성
│  ├─ AI Intake
│  ├─ Case Report
│  └─ Case Workspace
│
├─ 사건 도구
│  ├─ 계산 엔진
│  ├─ 문서 생성
│  ├─ 증거 체크
│  └─ 절차 안내
│
├─ 가이드
│  ├─ 근로자
│  └─ 사업주
│
├─ 전문가 찾기
│  ├─ 검색
│  ├─ 프로필
│  └─ 상담 요청
│
├─ 사업주
│  └─ 예방·점검 중심 별도 진입
│
└─ 운영
   ├─ Admin
   └─ 향후 노무사 Portal
```

### 기존 기능의 역할 변경

| 기존 기능 | 1.0에서의 역할 |
|---|---|
| AI 상담 | 사건 Intake + 분석 인터페이스 |
| 상황별 해결 | Case Template / 대표 사건 진입점으로 흡수 |
| 계산기 | Case 내부 계산 엔진 + 독립 SEO 도구 |
| 문서센터 | Case 데이터 기반 문서 생성 엔진 + 독립 검색 |
| 상담요약서 | Case Report의 전문가 전달 버전으로 통합 |
| 노동청 절차 | Case Action Plan의 공식기관 단계 |
| 노무사 찾기 | 사용자가 필요할 때 선택하는 후단 연결 |
| 가이드 | SEO·교육·사건 이해 보조 콘텐츠 |
| 사업주 기능 | 별도 제품 영역으로 분리 |

## 6. AI 제품 설계

### AI의 역할

AI는 답변 생성기가 아니라 다음 5개 역할을 수행한다.

1. 사건 유형 분류
2. 누락 사실 탐지
3. 사용자 표현을 구조화된 사건 데이터로 변환
4. 검증된 법률 지식·계산 결과를 사람이 이해할 수 있게 설명
5. 다음 행동을 우선순위화

### AI가 직접 결정하지 않아야 하는 것

- 법정 금액의 핵심 계산
- 날짜·기한 산식
- 최저임금 등 연도별 법정 상수
- 적용 조건이 명확한 규칙 판단

가능한 부분은 결정론적 Legal/Calculator Engine이 계산하고 AI는 이를 설명한다.

### 목표 파이프라인

```text
사용자 입력
↓
Case Classifier
↓
Required Facts Engine
↓
Case State
↓
Legal Rules + Official Knowledge
↓
Calculator Engine
↓
Action Planner
↓
AI Explanation
↓
Case Report 업데이트
```

### 답변 품질 원칙

- 확인된 사실과 추정을 구분한다.
- 추가 확인이 필요한 사실을 숨기지 않는다.
- 법령·공식 근거의 기준일을 관리한다.
- 과거 학습 수치보다 검증된 지식 데이터가 우선한다.
- 단정적 승소·위법 확정 표현을 피한다.
- 긴 설명보다 다음 행동이 분명해야 한다.

## 8. UX / Design 원칙

### 디자인 목표

**예쁜 법률 사이트가 아니라, 불안한 사용자가 이해하고 행동할 수 있는 제품.**

### 8가지 원칙

1. 한 화면의 Primary Action은 하나다.
2. 사용자가 현재 단계와 남은 단계를 알 수 있다.
3. 중요한 판단·금액·기한은 시각적으로 명확하게 구분한다.
4. 법률용어보다 생활 언어를 우선하고 필요 시 정확한 용어를 병기한다.
5. 경고·예외·미확인 사실은 숨기지 않는다.
6. 모바일 360px부터 완전한 사용이 가능해야 한다.
7. 로딩·빈 상태·오류·만료·오프라인 상태도 정상 화면으로 설계한다.
8. 색상·카드 장식보다 정보 위계와 다음 행동을 우선한다.

### 제품 핵심 컴포넌트

기존 Button/Card/Input 외에 아래를 1급 컴포넌트로 만든다.

- CaseCard
- CaseProgress
- FactChecklist
- IssueCard
- MoneyResult
- DeadlineCard
- EvidenceChecklist
- ActionStep
- LegalCitation
- Confidence/Unknown State
- DocumentCard
- ExpertHandoff

## 9. 인사야 1.0 Release Scope

### 반드시 제품 수준으로 완성할 핵심 사건 5개

1. 임금체불
2. 해고·권고사직
3. 퇴직금
4. 근로시간·각종 수당
5. 연차

각 사건은 아래 항목을 처음부터 끝까지 지원해야 한다.

```text
진입
→ 필수 사실 확인
→ 쟁점 정리
→ 계산
→ 증거
→ 기한
→ 문서
→ 행동 순서
→ 공식 절차
→ 전문가 전달
```

### 기존 기능은 유지

- 27종 계산기
- 24종 문서
- 33종 이상 가이드/정적 SEO 콘텐츠
- 노무사 데이터/검색
- Admin
- 예약/리드
- 보안 요약 링크

다만 1.0 출시 판단은 기능 개수가 아니라 핵심 5개 사건의 완결성으로 한다.

## 10. 사업주 제품 방향

인사야 1.0의 주 홈은 근로자 문제 해결을 우선한다.

사업주는 별도 진입 후 다음 흐름으로 설계한다.

```text
사업장 기본정보
↓
노무 위험 진단
↓
위험 항목
↓
필요 조치
↓
계약/문서/계산
↓
전문가 자문
```

핵심 영역:

- 근로계약
- 임금·근태
- 상시근로자 수
- 해고 전 체크
- 취업규칙
- 연차관리
- 법정의무 자율점검

근로자 Case UX와 동일 화면에 섞지 않는다.

## 11. 전문가 연결과 수익모델

### 사용자

근로자는 핵심 해결 도구를 무료로 사용할 수 있다.

### 노무사

가능한 수익원:

- 입점 구독
- 프로필 강화
- 스폰서 노출
- 지역/분야 광고
- 예약관리 SaaS
- 상담 CRM

하지 않는 모델:

- 사건당 소개 수수료
- 수임료 비율
- 성공보수 연동

### 사업주

향후 유료화 후보:

- 고급 자율점검
- 사업장 문서관리
- 법정 일정/리마인더
- 인사노무 템플릿
- 전문가 자문 구독 연계

## 12. Product Metrics

### North Star Metric

**사건 해결 준비 완료율**

`사건 생성 → 필요한 사실 확인 → 최소 1개 구체적 해결 행동 실행` 비율

### 핵심 퍼널

```text
방문
→ 사건 시작
→ Intake 1단계 완료
→ Case Report 생성
→ 계산/증거/문서 중 행동 실행
→ 공식 절차 또는 전문가 연결
```

### 보조 지표

- 사건 시작률
- Intake 이탈률
- Case Report 생성률
- 계산 완료율
- 문서 생성률

## 14. 개발 원칙

1. 기능 추가보다 핵심 사건 완결을 우선한다.
2. `main`은 배포 가능한 기준 브랜치다.
3. 큰 리팩터링은 기능 보존 테스트 후 단계적으로 한다.
4. 거대한 `index.html`을 한 번에 프레임워크로 재작성하지 않는다.
5. 법률 데이터·계산식·콘텐츠를 UI에서 점진적으로 분리한다.
6. 생성된 SEO 페이지와 원본 데이터의 책임을 명확히 한다.
7. 기능을 만들 때 정상상태뿐 아니라 오류/빈/로딩 상태까지 동시에 만든다.
8. 제품 기능의 완료 정의에는 테스트와 문서 업데이트가 포함된다.

## 16. 기존 기획문서와의 관계

이 문서는 2026-08-14부터 **제품 방향의 최상위 기준**으로 사용한다.

기존 `PRODUCT.md`, `MASTERPLAN.md`, `UPGRADE.md`, `POLISH.md`, `PAGES.md`, `DESIGN.md`, `CONTENT.md`, `HARVEST.md`, `OPERATIONS.md`에는 유효한 세부 아이디어가 많이 있으나 작성 시점과 구현 상태가 서로 다르다.

따라서 기존 문서는 삭제하지 않고 우선 보존하며:

1. 실제 구현 여부를 `docs/STATUS.md`에서 다시 판정하고,
2. 유효한 기획은 본 문서/향후 세부 스펙으로 승격하고,
3. 역할이 끝난 문서는 `docs/archive/`로 이동한다.

새 기능은 기존 문서의 TODO만을 근거로 착수하지 않는다.
